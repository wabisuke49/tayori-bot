# Issue Grill

指定Issueを、別の開発者やCodexが実装に着手できる状態まで具体化する。
質問攻めにするのではなく、**自分で調べられることは調べ、ユーザーだけが決められることを1問ずつ聞く**。

## 入力

- GitHub Issue番号（例: `#123`）またはIssue URL。
- 任意で、重視したい観点（UX、API、移行、セキュリティ、スコープなど）。

Issueを特定できない場合は、番号・URL・本文のいずれかを求める。

## 事前調査

1. `AGENTS.md`、`README.md`、関連ドキュメント、`.github/ISSUE_TEMPLATE/` を読む。
2. `gh issue view <番号> --json title,body,state,labels,comments,url` などでIssueとコメントを取得する。URLがあれば対象リポジトリを取り違えない。`gh` が使用できなければ、ユーザーが提供したIssue本文を使い、未取得であることを明記する。
3. 関連コード、テスト、設定、既存APIや類似機能、関連Issueを調べる。既存実装から分かる事実と、Issueで決めるべきことを分ける。
4. 論点を洗い出す。特に目的、スコープ、期待する動作、異常系、境界条件、データ/API互換性、権限、移行、テスト可能な完了条件を確認する。関係のない観点は質問しない。
5. 不明点を **「調査で解決」「推奨案あり」「ユーザー判断が必要」** に分類し、ユーザー判断が必要な論点から優先順位を付ける。

## Grill Me の進め方

1. **1ターンにつき質問は必ず1問だけ**。複数の独立した判断を一度に聞かない。
2. 各質問には、背景を1〜2文で添え、可能なら2〜4個の具体的な選択肢を出す。
3. 選択肢には**推奨案とその理由**を示す。トレードオフがあれば短く併記する。「その他」「判断保留」も許容する。
4. ユーザーの回答を要約して決定事項に追加し、必要に応じて次の1問へ進む。回答を勝手に拡大解釈しない。
5. コードや文書で確認できる内容、既に答えが明確な内容は質問しない。低影響の詳細は、合理的な仮定を置き「提案」として扱ってよい。
6. 追加質問が不要になった時点、またはユーザーが「終了」「まとめて」と指示した時点で質問を止め、結果をまとめる。途中終了の場合は未決事項を残す。

### 質問例

> Issueでは「保存失敗時に通知する」とありますが、ユーザーが再試行できるようにする範囲が未定です。どちらにしますか？
>
> A. エラー表示のみ
> B. エラー表示＋再試行ボタン（推奨：一時的な失敗から復帰しやすいため）
> C. 自動再試行
>
> どれにしますか？

これは書式の例であり、実際の質問は調査結果に即して作る。

## 終了条件

次の状態になれば、十分に具体化されたと判断する。

- 目的と解決すべき課題が明確。
- 対応範囲と対象外が区別されている。
- 外部から観測できる振る舞いと重要な異常系が決まっている。
- 受け入れ条件がチェック可能。
- 実装を妨げる重大な未決事項が解消済み、または未解決として明示されている。

## 最終出力

以下の順で日本語でまとめる。

1. **決定事項**：何を決めたか。必要なら判断理由。
2. **未決事項・前提**：残る不確実性と影響。
3. **改訂Issue案**：元Issueの意図を保持した、GitHubに貼れる完成形のMarkdown。既存Issueテンプレートがあれば従う。
4. **差分要約**：元Issueから追加・変更した主な点。

改訂Issue案には原則として「背景・課題」「目的」「対応範囲」「受け入れ条件」「対象外」「関連情報」「未決事項」を含める。無関係な項目は省略してよい。

## GitHub更新のルール

- **初期動作は閲覧と対話のみ。** Issue本文・コメント・ラベル・ステータスを自動更新しない。
- ユーザーが明示的に「この内容でIssueを更新して」と承認した場合に限り、対象Issueを再取得して競合する変更がないか確認し、改訂本文を `gh issue edit` 等で反映する。
- 更新前に最新内容が変わっていた、権限がない、Issueを特定できない場合は無理に上書きしない。
- コード実装、ブランチ・PR作成は行わない。

## 呼び出し例

- `$issue-grill #123 の仕様を深掘りして`
- `$issue-grill https://github.com/owner/repo/issues/123 をGrill Meして`
