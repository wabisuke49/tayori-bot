# Issue Draft

ユーザーの要望から、開発者が着手できる日本語のGitHub Issue案を作成する。
**このスキルはドラフト作成専用**。Issueの投稿、コード変更、コミット、ブランチ操作は行わない。

## 入力

- ユーザーが提示した課題、要望、バグの症状、または改善したい内容。
- 必要に応じて、対象リポジトリ、参考URL、制約、希望する優先度。
- 入力が短くてもまず調査し、回答不能な重要事項だけ確認する。

## 手順

1. **プロジェクトの前提を確認する。** `AGENTS.md`、`README.md`、関連仕様書、`.github/ISSUE_TEMPLATE/` を確認する。Issueテンプレートや記述ルールがあれば優先する。
2. **関連実装を調べる。** `rg` などで対象コード、テスト、設定、既存の振る舞いを確認する。見つかった事実はファイルパスとともに控える。コードにない仕様を断定しない。
3. **重複・関連Issueを調べる。** GitHub CLI (`gh`) が利用でき、対象リポジトリにアクセス可能な場合は、キーワードでopen/closed両方のIssueを検索する。権限やネットワークの問題で調べられない場合は、その旨を記す。
4. **解くべき課題を定義する。** 「何が起きているか」「なぜ解決するか」「何を実現すれば完了か」を分離する。原因が未確認なら推測と明記する。
5. **スコープを決める。** 対応範囲と対象外を明示する。独立して実装・検証できる大きな要求は複数Issueへの分割を提案する。ただし、ユーザーの同意なくGitHub上で分割・起票しない。
6. **受け入れ条件を書く。** 実際に検証可能なチェック項目にする。必要なら正常系、異常系、境界値、既存機能への影響を含める。実装方法を過剰に固定しない。
7. **不明点を残す。** 必要な判断が未確定なら「未決事項」に記載する。重大な不明点によりIssue案が成立しない場合だけ、焦点を絞った質問をする。

## 出力

まず `タイトル案` を1つ提示し、その後に**GitHubへコピーできるMarkdown本文**を出す。リポジトリにIssueテンプレートが存在する場合は、その形式を優先する。テンプレートがない場合は以下を使う。

```markdown
## 背景・課題
<!-- 現状、困っていること、根拠 -->

## 目的
<!-- 解決した後に実現したい状態 -->

## 対応範囲
-

## 受け入れ条件
- [ ]
- [ ]

## 対象外
-

## 関連情報
<!-- 関連コード、仕様、Issue、ログ。確認できたもののみ -->

## 未決事項・リスク
-
```

出力の最後に、必要に応じて「関連Issue候補」「分割すべきIssue」「確認が必要なこと」を短く補足する。該当しないセクションは空欄のままにせず、省略するか「なし」と記す。

## 品質ルール

- タイトルは課題や達成したい状態が分かる簡潔な日本語にする。既存の命名規則に合わせる。
- **確認できた事実・推測・提案を区別する。** テスト済み、再現済み、既存Issue確認済みなどを偽って書かない。
- 受け入れ条件には「適切に」「問題なく」だけの曖昧な表現を使わない。
- 単なる実装タスクの羅列ではなく、ユーザー価値と完了条件を明確にする。
- API・DB・認可・互換性・移行が関係する場合は、影響範囲や確認事項を含める。
- 認証情報、個人情報、機密ログはIssue案に転載しない。
- **GitHub Issueを作成・編集しない。** 起票が必要な場合は、作成した案を提示し、別途明示的な起票依頼を求める。

## 呼び出し例

- `$issue-draft パスワード再設定時にエラーが表示されないので改善Issue案を作って`
- `$issue-draft この認証周りの技術的負債をIssueに整理して`
