# PR Create

現在の作業内容を確認し、レビューしやすいGitHub Pull Requestを作成する。
**PR作成の依頼はpushとPR投稿の許可として扱ってよい**が、無関係な変更の混入、破壊的なGit操作、機密情報の公開は避ける。

## 前提

- Gitリポジトリ内で作業していること。
- `git` が使え、PR投稿先へのアクセスと `gh` の認証があること。
- リポジトリ固有の方針（`AGENTS.md`、`CONTRIBUTING.md`、`.github/PULL_REQUEST_TEMPLATE.md` など）を優先する。
- 前提を満たさなければ、できたところまでのPR本文案と不足条件を示す。作成したと偽らない。

## 手順

1. **投稿先とブランチを特定する。** `git status --short`、`git branch --show-current`、`git remote -v`、`gh repo view --json defaultBranchRef` などを確認する。ベースブランチはユーザー指定を最優先し、指定がなければリポジトリのデフォルトブランチにする。
2. **作成済みPRを確認する。** 現在ブランチのPRが既にある場合は新規作成を重複させず、URLと状態を示す。変更が必要ならその内容を確認する。
3. **実際の差分を調べる。** ベースブランチとのコミット・差分、ステージ済み・未ステージ・未追跡ファイルを確認する。変更目的、影響範囲、潜在的な破壊的変更を把握する。コミットメッセージだけで内容を判断しない。
4. **機密・不要ファイルを確認する。** `.env`、鍵、トークン、個人情報、ビルド生成物、大容量ファイルなどをコミット・push対象に含めない。疑わしい場合は作業を止めて確認する。
5. **差分を検証する。** `git diff --check` を実行し、プロジェクトの指示に従って影響範囲に適切なテスト、lint、型チェック等を実行する。実行できなかった検証は理由を記録し、成功したと表現しない。
6. **必要なコミットを作る。** 未コミット変更があり、今回の依頼に属するファイルを明確に特定できる場合のみ、そのファイルを個別指定でステージし、リポジトリの規約に沿ってコミットする。無関係な変更が混在する、意図が不明な場合は確認する。変更がすでに適切にコミットされていれば追加コミットしない。
7. **安全にpushする。** 作業ブランチがベースブランチ自身なら、作業を確認して別ブランチを作成する。`git push -u origin <branch>` など通常のpushを使う。force push、reset、rebase、既存コミットの書き換えは、このスキルの標準手順では行わない。
8. **PR本文を作る。** `.github/PULL_REQUEST_TEMPLATE.md` または既存PRの慣習に合わせ、下記の情報を事実に基づいて記載する。
9. **PRを作成する。** 通常はレビュー可能なPRを作る。検証失敗、重要な未完了作業、ユーザーの指定がある場合はDraft PRにする。`gh pr create` の適切なオプションを使い、作成結果のURLを確認する。
10. **結果を報告する。** PR URL、タイトル、base/head、変更の要約、実行した検証の結果、未対応事項を簡潔に伝える。

## PR本文の基本形

リポジトリのPRテンプレートがある場合は、次の書式よりそちらを優先する。

```markdown
## 概要
<!-- このPRで何を、なぜ変更したか -->

## 主な変更点
-

## 関連Issue
<!-- 完全に解決する場合だけ Closes #123、関連付けのみなら Refs #123 -->

## 確認内容
- [ ] <!-- 実行した検証と実際の結果を記載 -->

## 影響範囲・注意事項
<!-- 互換性、移行、既知の制限、未検証事項など -->
```

- テストを実行したならコマンドと結果を記す。未実行の場合は「未実行（理由）」と書く。
- スクリーンショットが必要なUI変更なら、用意できた場合にのみ添付し、未取得なら明示する。
- 関連Issueが完全に解決する場合だけ `Closes #123`、部分対応なら `Refs #123` を使う。根拠がない番号は創作しない。
- 変更と無関係なチェック項目やセクションは削除してよい。

## 絶対に避けること

- `git add .` や `git add -A` による無差別ステージング。
- ユーザーの既存変更を破棄する `reset --hard`、`clean -fd`、無断のstash、force push。
- テスト失敗の隠蔽、未実行テストの「成功」扱い。
- 既存PRの重複作成や、レビューを受けていない状態での自動マージ。
- 関係のないコード修正をPR作成のために勝手に追加すること。

## 呼び出し例

- `$pr-create 今のブランチの変更からPRを作成して`
- `$pr-create #123 に対応した変更をDraft PRで出して`
